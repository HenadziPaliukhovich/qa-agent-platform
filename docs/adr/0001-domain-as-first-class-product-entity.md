# ADR 0001: Domain as a first-class product entity

## Status

Proposed

## Context

Текущая архитектура платформы уже содержит foundation для task execution, orchestration, LLM gateway и knowledge storage. Однако текущая продуктовая модель фактически опирается на сущности `project_id` и `service_name`, что недостаточно для целевой платформы.

Платформа должна поддерживать:
- настраиваемый контекст для LLM;
- запуск задач и workflow в рамках выбранной предметной области;
- конфигурируемость через UI;
- отсутствие жёсткой привязки к одному типу продукта или одному стеку.

Если оставить модель только на `project/service_name`, то:
- контекст останется слишком технически ориентированным;
- UI не сможет управлять доменной моделью как продуктовой сущностью;
- добавление новых предметных областей будет требовать изменений в коде;
- платформа начнёт жёстко наследовать структуру тестируемой системы, а не нужды QA-процесса.

Для целевой платформы нужен такой уровень абстракции, который:
- ближе к реальной QA-работе;
- не зависит жёстко от структуры микросервисов;
- позволяет управлять контекстом, политиками и execution scope через UI.

## Decision

Принято решение ввести `Domain` как first-class product entity.

`Domain` становится основной пользовательской сущностью, через которую организуются:
- контекст;
- запуск задач;
- запуск workflow;
- артефакты;
- настройки поведения платформы;
- привязка интеграций и источников событий на продуктово-логическом уровне.

Также вводится связанная сущность `DomainProfile`.

Разделение ответственности:
- `Domain` хранит идентичность и жизненный цикл домена: `domain_id`, `name`, `slug`, `description`, `status`, `tags`.
- `DomainProfile` хранит конфигурацию поведения платформы внутри домена: `business_scope`, `prompt_policy`, `retrieval_policy`, `supported_artifacts`, `event_source_settings`, `integration_bindings`.

Ключевые правила решения:
- Домены должны создаваться и редактироваться из UI.
- Список доменов не должен жить только в коде.
- Платформа может поставляться с преднастроенными доменами, но они считаются seed configuration, а не hardcoded-only model.
- Большинство типовых доменных сценариев должно поддерживаться без изменения ядра платформы.
- Кодовое расширение допускается только для действительно специализированного поведения, а не для базового жизненного цикла домена.

`Domain` становится основным execution scope для thin-slice модели:
- задача запускается в рамках домена;
- retrieval ограничивается доменом;
- артефакты и результаты помечаются доменом.

## Consequences

Плюсы:
- продуктовая модель становится ближе к реальной работе QA;
- UI получает понятную сущность для управления контекстом и execution scope;
- платформа становится расширяемой для новых предметных областей;
- снижается жёсткая привязка к структуре конкретной системы или стека;
- появляется фундамент для domain-aware workflow и explainable artifacts.

Минусы и компромиссы:
- потребуется миграция от текущей модели `project/service_name`;
- появится новая сущность конфигурации, которую надо проектировать аккуратно, чтобы не усложнить платформу преждевременно;
- часть доменного поведения всё равно останется code-defined на ранних этапах;
- возрастёт сложность API, UI и data model.

Дополнительные последствия:
- нужно определить границу между configurable behavior и code extension;
- нужно отдельно спроектировать миграцию знаний и task execution на `domain_id`;
- нужно обеспечить backward compatibility на переходный период.

## Alternatives considered

- Оставить текущую модель на `project_id` и `service_name`.
- Ввести только `service_name` как основной execution scope.
- Сделать список доменов захардкоженным в backend и UI.
- Построить доменную модель исключительно через кодовые handler-ветвления без UI-конфигурации.
